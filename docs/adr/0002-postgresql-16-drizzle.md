# ADR-0002: PostgreSQL 16 with Drizzle ORM

## Status
Accepted

## Date
2026-10-27

## Context
The data is relational: Account → Deal → Quote → Sales Order → Invoice. Money must be exact. Tenancy is enforced by Row Level Security (ADR-0003). Custom fields need a JSONB column (ADR-0006). We want typed queries but full control of the SQL that RLS and triggers depend on.

## Decision
- **PostgreSQL 16** (RDS in prod, Docker image `postgres:16` in dev and CI).
- **Drizzle ORM 0.45.x + drizzle-kit 0.31.x** (stable line). On the stable line, RLS uses `pgPolicy(...)` and `.enableRLS()`. `pgTable.withRLS` exists only in the v1 beta, so we do not use it until v1 is GA.
- Migrations are generated by drizzle-kit as SQL files, **reviewed and committed**, and applied with `pnpm db:migrate`. Hand-written SQL migrations hold policies, triggers, grants and `SECURITY DEFINER` functions that drizzle-kit cannot express.
- Money and rate columns use `numeric(p,s)` mapped with `mode: 'string'`, so values never pass through JS `number` (ADR-0007).
- Primary keys are UUID v7, generated in the app. They sort by time, which keeps indexes local, and they don't leak counts the way serial ids do.
- Every schema change ships a migration and an update to `docs/SCHEMA.md` (CLAUDE.md rule).

## Alternatives considered
- **Prisma.** Its RLS story requires extensions, and it is less direct for `set_config` in a transaction. Rejected.
- **Kysely.** Viable, but it has no schema-as-code migrations. Rejected to keep one source of truth.

## Consequences
- The schema lives in TypeScript (`packages/db`) and the SQL is reviewable.
- RLS policies and triggers live partly in hand-written SQL. A CI test asserts that every tenant table has RLS enabled (ADR-0003).
